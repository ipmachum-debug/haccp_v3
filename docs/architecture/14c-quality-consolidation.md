## 2. 비교표

### 2-1. 부적합

| 항목 | 식품 구형 (부적합제품관리) | 공통 (`/quality/nonconforming`) |
|---|---|---|
| 테이블 | `h_nonconforming_products` + 통계 · 첨부 테이블 | `h_nonconformings` (단일) |
| 데이터 | **0건** | **0건** |
| 필드 | 발견일·발견경로·제품·LOT·**배치·제품 ID·사업장**·수량·유형·내용·원인·처리방법·처리일·비용·발견자·책임자·승인자·CAR 연결·예방조치·비고·작성자 | 같은 필드에서 **배치·제품 ID·사업장·작성자 컬럼 없음**, 대신 업종·업종별 메타데이터(JSON)·품목명 |
| 상태 흐름 | 발견 → 조사 중 → 처리 대기 → … (+ 별도 **승인** 동작) | 같은 상태값을 상태 전이(transition)로 진행, 승인자 필드는 있음 |
| 첨부 | 첨부 테이블 있음 | 없음 |
| 출력 | 전용 인쇄 없음 (목록 내보내기) | 전용 인쇄 없음 (목록 내보내기) |
| 함께 있는 기능 | **회수 시뮬레이션** 탭 (별도 테이블) | — |
| 연결 | AI 컨텍스트가 참조 | 공통 CAPA 와 연결(부적합 ID) |

**판단**: 공통 부적합은 식품 구형을 일반화한 설계다. 식품이 공통으로 옮겨도 잃는 것은 **배치·제품 연결, 첨부, 별도 승인 동작** 3가지. 두 테이블 모두 0건이라 옮길 데이터는 없다.

### 2-2. 시정조치

## 3. 결정이 필요한 것 (대표)

1. **식품 부적합을 공통으로 옮길지** — ✅ **이행 (2026-10-14 대표 결정)**. 선행 3가지 재확인 결과:
   - 배치·제품 ID: 구형 화면에서도 입력 칸이 없었다(스키마에만 존재) → 손실 없음. LOT 번호는 양쪽 모두 입력
   - 첨부: 구형 서버 함수만 있고 화면에서 쓰지 않았다 → 손실 없음
   - 승인: 구형 approve = 상태 '처리 완료' + 승인자 기록(권한 확인 없음). 공통 '처리 완료' 전이 = 같은 기록 + admin 권한 확인 → 동등 이상
   - **실제 차이는 원인 분석·처리 입력** — 공통 화면에 서버 API(setRootCause·setDisposal)는 있었지만 입력 칸이 없었다 → 공통 화면에 '원인·처리' 입력 창 추가 (전 업종 혜택)
   - 메뉴: 식품 '부적합제품관리' → /quality/nonconforming, 구형 화면의 탭이던 **회수 시뮬레이션은 독립 메뉴**(/recall-simulation)
   - 옛 경로 /dashboard/nonconforming-management · /nonconforming-products → 공통 부적합 리다이렉트
   - AI 컨텍스트의 부적합 쿼리를 공통 테이블로 (구형 쿼리는 없는 칸을 읽어 실패하던 상태)
   - 구형 서버 라우터·테이블(h_nonconforming_products, 0건)은 남겨 둔다 — 화면 없음, 4단계 뒤 폐기 판단
2. **식품 시정조치** — 권장: **CAR 유지**. 공통 CAPA 는 식품에서 부적합·감사 후속용으로 함께 쓰되 메뉴명으로 구분("CCP 시정조치" / "CAPA").
3. **검교정** — 양쪽 모두 0건, 실사용 전이므로 하나로 정할지 결정. 두 화면의 필드·기능(성적서·판정·다음 교정일 등)은 이 표에서 아직 비교하지 않았다 — 결정 전 별도 비교.
