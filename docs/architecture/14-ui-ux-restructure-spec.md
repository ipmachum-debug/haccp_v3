## 0. 목표와 성공 기준

> **117개 메뉴를 50개로 줄이는 것이 성공이 아니다. 사용자가 117개의 존재를 몰라도 자기 업무를 끝내는 것이 성공이다.** (CEO, 2026-10-14)

1. **찾기 쉽다** — 업무 이름으로 들어간다 (구매·입고, 생산관리 …). 기능 이름으로 찾지 않는다.
2. **한 업무를 여러 메뉴로 돌지 않는다** — 업무의 입구는 하나, 기능은 필요한 순간에 보인다.
3. **업종·권한이 달라도 같은 방식으로 쓴다** — 공통 업무 메뉴 + 업종별 기능 구성 + 사용자별 권한.

**판정 기준 (4단계에서 측정)**: 같은 업무를 개편 전·후에 수행했을 때 **클릭·화면 이동은 줄고, 기능과 권한은 그대로**이며, **기존 URL·즐겨찾기는 모두 동작**한다.

**바꾸지 않는 것**: 데이터 처리 로직의 정본 — `ItemIdentityService`(품목 정체성), 재고 관문(`applyInventoryDelta`·음수 정책), CCP 공식 기록지 정본, 업무 FK, 서버 권한 검사. **메뉴의 통합과 업무 로직의 통합은 다른 작업이다.**

**허브 8개 이름·순서는 위 표대로 확정** (CEO, 2026-10-14). 플랫폼 관리는 슈퍼관리자 전용으로 별도 유지.

**각 허브는 메뉴 모음이 아니라 업무의 시작점이다. 허브 안에 수많은 탭을 나열하는 방식은 금지한다.** 생산관리에 들어가 15개 탭이 보이면 지금과 같다. 허브 = 입구 화면(지금 처리할 것) + 업무를 고르면 그 업무 화면으로 이동. 탭은 **같은 대상의 다른 면**(예: 거래처 상세의 기본정보·CRM·커뮤니케이션)에만 쓴다.

역할별 첫 화면의 뜻: 대표는 8개 허브를 하나씩 열지 않고 **한 화면**에서 오늘 생산이 정상인지, 재고 문제가 있는지, 승인할 문서가 있는지, 미수금이 얼마인지 본다. 현장 작업자는 회계·재무보고·신용관리 메뉴의 **존재를 알 필요가 없다**.

| 생산계획·생산지시 ↔ 생산실적 | 계획·지시는 의도, 실적은 결과 기록 |
| 배합·BOM ↔ 실제 원재료 투입 | 기준정보 vs 투입 기록(LOT·수량) — 권한·이력 요건이 다름 |

## 4. 메뉴 정의 정본화 (2단계)

### 4-1. 메뉴 레지스트리 한 곳

`shared/navigation/menuRegistry.ts` (타입·상수만 — shared-kernel 규칙 준수). 사이드바·모바일 하단바·즐겨찾기·`childRoutes`·브레드크럼·라벨 치환·부록 14a 표를 **모두 여기서 생성**한다.

```ts
interface MenuEntry {
  id: string;                 // 안정 키 (즐겨찾기 저장용, 경로가 바뀌어도 유지)
  hub: HubId;                 // today | purchase | items | production | quality | sales | finance | settings | platform
  label: string;              // 업종 용어는 labelKey 로 치환 (useIndustryLabel)
  path: RoutePath;            // ROUTES 상수만
  childPaths?: RoutePath[];   // 상세·하위 화면 (활성 메뉴 판정)
  feature: FeatureArea;       // rbacMatrix 기능 영역
  permission: Permission;     // 이 메뉴를 보려면 필요한 권한 (보통 read)
  industries?: IndustryKey[]; // 없으면 공통. 있으면 해당 업종 테넌트만
  module?: "haccp" | "erp";   // 구독 모듈
  mobile?: boolean;           // 모바일 하단바·빠른 메뉴 노출
  order: number;
  legacyPaths?: string[];     // 옛 URL → 이 항목으로 리다이렉트
}
```

- **노출 판정 = 업종 ∩ 모듈 ∩ 권한** — 하나의 함수 (`visibleMenu(user, tenant)`). 탭(WORK/회계/HACCP)별 출처 분기 삭제.
- 업종 플러그인의 `menu.groups` 는 **업종 전용 기능 목록**(`industries` 지정 항목)으로만 남긴다. 공통 메뉴를 플러그인이 다시 정의하지 않는다.
- 업종 품질 8종은 **공통 경로 1벌**(`/quality/nonconforming` 등) + 업종은 테넌트 설정에서. 업종별 차이(필수 항목·승인 단계·보존 기간·용어)는 정책 데이터(04-policy-registry). 기존 `/dashboard/{업종}/{기능}` 48개는 `legacyPaths` 로 리다이렉트.

### 4-2. 권한 — 메뉴와 서버가 같은 매트릭스를 보되, **매트릭스부터 재검토한다**

**기존 `rbacMatrix.ts` 를 그대로 서버 전체에 적용하지 않는다** (CEO). 적용된 적 없는 표라 아래 값이 검증되지 않았다.

| 역할 | 현재 표 | 재검토 결과 (초안 — 0-2 PR 에서 CEO 확정) |
|---|---|---|
| `monitor` | accounting / inventory / production **approve** | 품질검토자. 회계·재고·생산 승인은 **제거**. haccp·inspection approve 만 |
| `accountant` | inventory **write** | 회계 담당자. 재고 **read·export** 로. 입고·조정은 inventory 권한 보유 역할만 |
| `accountant` | accounting approve | **초기 개편에서는 admin 유지** (아래) |
| `inspector`, `worker` | approval **write** | "승인 요청 생성" 의미라면 유지, "승인" 이면 제거 — 의미를 `request` 로 분리 |
| `employee` | 전부 false | 본인 정보(공지·출퇴근·교육)만 — `self` 범위 추가 |

**회계 담당자 권한 (CEO 결정, 단계적 허용)**
- 허용: 조회 · 작성 · 수정 · 전표 등록 · 재무보고 · 회계자료 내보내기
- **매출·매입 확정은 초기 개편에서 관리자(admin) 권한 유지.** 확정은 재고 차감·분개와 연동되므로 §2 의 선행 조건 5개가 충족된 뒤 확장. 확장할 수 있게 **작성·확정·취소·역분개를 별도 permission 으로 설계**한다 (`write` / `post` / `cancel` / `unpost`).

**서버 검사 원칙**: 메뉴 표시 여부는 권한이 아니다. 서버는 **테넌트 · 역할 · 대상 데이터의 소유권 · 업무 상태**를 함께 검증한다 (예: 다른 테넌트 전표 id 거부, 취소된 전표 확정 거부).

- 매트릭스 위치: `shared/permissions/rbacMatrix.ts` 로 옮겨 클라이언트·서버가 같은 표를 쓴다 (재검토된 값으로).
- 메뉴: `permission` 을 매트릭스로 판정. 메뉴 항목의 roles 배열 하드코딩 삭제.
- 서버: 라우터를 `adminProcedure`/`workerProcedure` 에서 `createFeatureProcedure(feature, permission)` 으로 점진 이주 (Strangler — 허브 단위 PR). 각 PR 에 **허용되어야 하는 호출과 차단되어야 하는 호출 양쪽 테스트**.
- 사용자별 예외가 필요해지면 DB 기반 `requireCapability`(04-policy-registry) 로 확장.

### 4-3. 기존 URL·즐겨찾기 보존

- 모든 기존 경로는 **그대로 열리거나** `legacyPaths` 리다이렉트로 새 위치로 간다. 404 0건이 완료 조건.
- 즐겨찾기(`menuPath` 저장)는 마이그레이션 시 레지스트리의 `legacyPaths` 로 해석 → 새 `id` 로 변환.

### 7-2. "오늘의 생산" 단계 순서 (CEO 확정 2026-10-14 — 재고 확인이 자동출고보다 먼저)

13 문서 §3 초안은 ② 시작(자동출고) 뒤에 ③ 재고 확인이 와서, 확인도 전에 차감되는 순서였다. 아래로 바꾼다.

| 단계 | 업무 | 처리 | 기존 기능 |
|---|---|---|---|
| ① | 오늘의 생산 | 생산지시 선택 | `batch.list` (planned_date = 업무일자) |
| ② | 배합·BOM 확인 | 필요 원재료 계산 | `h_batch_inputs` 투입 계획 |
| ③ | 재고·LOT 확인 | 가용재고 · 부족 · 유통기한 확인 | 재고 스냅샷 · LOT (FEFO 순) |
| ④ | 생산 시작 | **자동출고 1회 실행** | `batch.updateStatus(in_progress)` → 자동출고 dispatcher |
| ⑤ | 투입 결과 · HACCP 기록 | 실제 수불 및 공식 기록지 확인 | 자동출고 결과 LOT·수량, `h_ccp_form_records` 상태 |
| ⑥ | 생산완료 | 완제품 LOT · 재고 반영 | `completeBatch` → 승인 요청 |

이 PR(0-1·0-3)에서는 생산 시작·자동출고 코드를 바꾸지 않는다. 변경은 P-2 에서.

### 7-3. P-2 에서 반드시 확인할 것 (CEO)

- **③ 에서 확인한 시점과 ④ 시작 버튼을 누른 시점 사이에 다른 생산지시가 같은 LOT 를 썼을 수 있다.** 화면의 사전 검증만으로는 부족하다. **생산 시작 시점에 서버가 재고·LOT 를 다시 검증**하고, 같은 배치의 **중복 실행을 막는다** (시작 두 번 → 자동출고 한 번, #483 출고 기록 기반 방어 포함).
- **기존 음수 재고 정책을 이번 UI 개편에서 임의로 바꾸지 않는다.** 재고 부족을 무조건 음수로 처리하는 것이 아니라, 기존 정책(`negativeStockPolicy`: 허용 테넌트 조건, 금지 테넌트 예외)에서 음수 출고가 허용되는 조건과 승인 절차를 확인한다. "입고 대기" 라는 화면 표시만으로 재고 부족 처리의 정당성이 확보되는 것은 아니다.
- 완료(⑥) 는 이미 출고된 투입을 다시 차감하지 않는다 (기존 방어 유지).

### 7-4. 변경 원칙 (CEO)

**화면을 먼저 정리하고 → 기존 기능을 연결하고 → 데이터 정합성을 검증하고 → 마지막으로 기존 화면을 대체한다.** 재고·생산·회계는 서로 얽혀 있어 하나를 고치면 다른 기능이 영향을 받는다. 각 PR 은 이 네 단계 중 어디인지 밝힌다.
