# 13. 역할별 업무 화면 — 7단계 설계 초안

> 작성: 2026-10-12. 상태: **설계 초안 — CEO 검토 대기 (코드 없음)**.
> 선행: `11-identity-policy-v3.md` §3 7단계. 근거: 사이드바 메뉴 정의 실측(117개), 역할 enum, 2026-10-12 정밀진단 §7 (우선 사용자 업무 5개).

## 0. 원칙 (CEO·외부 진단, 2026-10-11~12)

1. **사용자에게 필요한 것은 기능 목록이 아니라 업무 처리 화면이다.** 메뉴의 존재를 몰라도 일이 끝나야 한다.
2. **메뉴를 합치는 것과 업무 흐름을 바꾸는 것은 다른 작업이다.** 탭 15개짜리 화면은 복잡함의 자리를 옮긴 것뿐.
3. **업종 품질관리는 공통 엔진 + 업종별 요구(기록·승인·보존)** — 라벨만 바꾸는 통합은 안 된다.
4. **측정으로 검증한다.** 같은 업무를 개편 전·후에 수행시켜 완료 시간·클릭 수·오류율·도움 요청 횟수를 비교.
5. 배포는 작게. 역할 하나, 화면 하나부터.

### 1-3. 역할 (실제 enum)
`super_admin · admin · accountant · worker · monitor · inspector · employee`. 지금은 역할과 무관하게 같은 사이드바를 보고, 역할은 메뉴 항목의 노출 여부만 가른다.

## 2. 설계 — 역할별 첫 화면 ("무엇을 해야 하는가" 가 먼저 보이는 화면)

| 역할 | 첫 화면 | 화면이 답하는 질문 | 사이드바 |
|---|---|---|---|
| **worker** (작업자) | **오늘의 생산** (§3) | 오늘 무엇을 만들고, 지금 어느 단계이고, 막힌 게 뭔가 | 접힘. 필요 시 "품목·재고", "현장 기록" 두 개만 |
| **inspector / monitor** (품질) | **오늘의 기록** | 오늘 써야 할 CCP·체크리스트·검사 중 안 쓴 것, 미측정·이탈 | 품질·규정 허브 |
| **accountant** (사무) | **회계 받은편지함** | 승인 대기 매입·매출, 미매칭 은행거래, 이번 달 마감 남은 것 | 구매 / 판매 / 회계·마감 허브 |
| **admin** (관리자·대표) | **운영 현황** + 결재함 | 오늘 생산·재고 부족·승인 대기·이상(FK/음수/미측정) | 전체 허브 |
| super_admin | 플랫폼 (변경 없음) | | |

"받은편지함" 은 승인 관리 + 알림 관리 + Today 를 **하나로** 합친 것이다. 세 곳을 돌며 확인하는 구조가 복잡함의 한 축이었다.

## 3. "오늘의 생산" — 기준 시나리오 (C. 하루 생산·CCP·자동 자재 차감)

한 화면, 위에서 아래로 6단계. 각 단계는 **이미 있는 엔드포인트**를 쓴다. 새 서버 로직은 없다.

> 2026-10-14 수정 (CEO 결정, 14 문서 §7-2): **재고 확인(③)이 생산 시작·자동출고(④)보다 먼저** 온다. 초안은 시작 뒤에 재고를 확인해 확인 전 차감되는 순서였다. 시작 시점의 서버 재검증·중복 실행 방지·음수 정책 준수는 14 문서 §7-3.

| 단계 | 화면에 보이는 것 | 데이터·동작 (기존) | 막힘 표시 |
|---|---|---|---|
| ① 오늘의 생산 — 생산지시 선택 | 오늘 날짜의 배치 카드 목록 (생산일 = `planned_date`, #457 업무일자). 카드를 누르면 아래 단계가 펼쳐짐 | `batch.list` (planned_date=오늘) / 주간 생산계획 | 배치 없음 → "생산지시 추가" 한 버튼 |
| ② 배합·BOM 확인 | 필요 원재료 계산표: 자재·필요량 | `h_batch_inputs` 투입 계획 (BOM 기준) | BOM 없음(#446 이후 거의 없음) |
| ③ 재고·LOT 확인 | 가용재고·부족·유통기한: 자재별 가용량, FEFO 순 LOT, 부족분 | 재고 스냅샷 + LOT | 가용 부족 → **"입고 대기 N"** 표시. 표시일 뿐 정당성 확보가 아니다 — 음수 출고 허용 조건·승인은 기존 정책(14 §7-3) |
| ④ 생산 시작 | "시작" 한 번 → 자동출고 1회 | `batch.updateStatus(in_progress)` → 자동출고 dispatcher. **P-2 에서 시작 시점 서버 재검증 + 중복 실행 방지** | 재검증 실패 → 사유와 함께 중단 |
| ⑤ 투입 결과·HACCP 기록 | 자동출고 결과(LOT·수량) 확인, 수동 보정은 여기서. 이 배치의 CCP 기록지·일일일지 상태 칩 (작성 전/미측정 N/완료) | `autoMaterialIssue` 결과, 조정은 `stockAdjustment`. `h_ccp_form_records`(batch_id), 일일일지 미측정 관문(#445) | 미측정 → 칩 클릭하면 그 기록지로 |
| ⑥ 생산 완료·재고 반영 | 실적 수량 입력 → 완료 | `completeBatch` → SKU LOT → 생산완료 분개 훅(#454) → 승인 요청 자동. 이미 출고된 투입은 다시 차감하지 않음 | 승인 대기 상태 표시 |

작업자는 생산관리·생산운영·제조기준관리·CCP 관리·일일일지·재고 메뉴의 존재를 몰라도 하루가 끝난다.

## 4. 정보구조 — 허브 8개와 117개 항목의 행선지

업무 흐름 순서: **사다 → 들이다 → 만들다 → 기록하다 → 팔다 → 맞추다**.

| 허브 | 들어가는 기존 화면 | 역할 |
|---|---|---|
| **오늘 할 일** | 오늘의 생산 / 오늘의 기록 / 받은편지함(승인·알림·Today) | 전원 (역할별 다른 첫 화면) |
| **구매·입고** | 발주·구매, 매입 등록·조회, 입고(재고 관리의 입고 탭), 거래처·단가표·신용 | admin, accountant |
| **품목·재고** | 품목 마스터 + 마스터 데이터 + 재고 관리 → 탭: 품목 / 재고 현황 / 실사 / 조정 / 수불부 | admin, accountant, worker(읽기) |
| **생산** | 생산관리 + 생산운영 + 제조기준관리(BOM) → 탭: 배치 / 계획 / BOM / 일보 | admin, worker |
| **품질·규정** | 현장 기록(CCP·체크리스트·검사·모바일·스캔 → "오늘 쓸 기록지" 한 목록) / 품질관리 8종(부적합·CAPA·변경·감사·교육·검교정·공급업체·위험) **1벌** / HACCP 검증·F-3 | inspector, monitor, admin |
| **판매·출고** | 견적서, 매출 등록·조회, 세금계산서, B2C 정산, 출고(재고 관리의 출고 탭) | admin, accountant |
| **회계·마감** | 비용, 은행, 전표, 부가세, 재무보고서, 자금, 예산, 급여·인사, 고정자산, 계정과목, 반복거래, 마감, 변경이력, 문서함 | accountant, admin |
| **관리자** | 시스템 관리, 데이터 임포트, 사내공지(배너), 연동, 사용자·권한 | admin |

### 업종 품질 48 → 8 로 가는 방법 (원칙 3)
- 메뉴·라우트·페이지는 **1벌**. 업종은 테넌트 설정(`industry`)에서 온다.
- 업종별로 다른 것 — 필수 기록 항목, 승인 단계, 보존 기간, 용어(CAPA vs 시정조치, AVL vs 공급업체) — 는 **정책 데이터**(04-policy-registry) 로 둔다. 코드에 `if (industry === …)` 금지(CLAUDE.md 절대 금지 3번).
- 현재 6벌의 페이지 중 실제로 다른 로직이 있는지 먼저 diff → 같으면 1벌로, 다르면 그 차이를 정책 데이터로 뽑는다. (6벌이 복사본일 가능성이 높다 — 확인은 7-b 에서)

### 중복 등록 정리
대시보드/통합 대시보드/Today 3곳 → 1, 알림 관리 2 → 받은편지함, 시스템 관리 2 → 관리자 허브.

## 5. 측정 — 개편 전 베이스라인부터

우선 업무 5개(정밀진단 §7)를 시연 시나리오로 고정하고, **개편 전에 먼저 잰다.**

| 시나리오 | 측정 |
|---|---|
| A 신규 제품 등록 → 배합 설정 → SKU 등록 | |
| B 원재료 발주 → 입고 → LOT 생성 | 완료 시간 · 클릭 수 · 화면 이동 수 · 오입력/재작업 · 도움 요청 |
| C 하루 생산 → CCP → 자동 자재 차감 → 완료 | |
| D 완제품 출고 → 재고 확인 | |
| E 회계 승인 → 전표 → 마감 | |

측정 방법: 1차는 사람이 스톱워치·클릭 카운트(같은 사람, 같은 데이터). 2차부터 화면 이동 로그(라우트 변경 횟수)를 클라이언트에서 간단히 남겨 자동화.

## 7. CEO 결정 요청 (3개)

1. **역할별 첫 화면 매핑(§2)** 이 현장과 맞는가. 특히 단지의 작업자가 쓰는 계정이 `worker` 인지, 품질 담당이 `inspector`/`monitor` 중 무엇인지.
2. **허브 8개 이름과 순서(§4)**. 현장 용어로 고치면 된다.
3. **파일럿**: 7-a 를 worker + "오늘의 생산" 으로 시작하는 데 동의하는가. 대안은 accountant + 받은편지함(회계 쪽 불만이 더 크면).

사용자 불만 목록(종류별 10개)이 있으면 §1-2 표와 대조해서 우선순위를 바꾼다.
